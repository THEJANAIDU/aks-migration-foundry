# Migration operator runbook

## Infrastructure checklist — independent of the application

- Select the infrastructure base branch, keep its checkout clean, and prepare the new infrastructure worktree.
- Review generated Bicep and parameters, network ranges/private DNS/agent access, cost/quota and identity permissions.
- Import the new Azure DevOps platform pipeline, replace all REPLACE values, review what-if, and obtain Ops approval before apply. Alternatively validate an existing platform against the same requirements and bootstrap the protected namespaces/quotas as a platform administrator.
- Verify AKS/ACR access, registry pull identity, namespace isolation, metrics-server/HPA, Pod Security, quotas, network policies and restore/monitoring arrangements.
- Create Environments and enforce Ops-owned production approvals outside YAML.

The generated infrastructure checklist says assets-prepared and live-validation-pending. It does not claim a cluster exists simply because files were written.

## Application checklist — blocked until proven containerized

- Review VM dependencies with the application owner. Identify local disk writes, databases, sessions, background jobs, OS dependencies and privileged host access. Metadata inventory alone is insufficient.
- Supply a committed Linux Dockerfile, committed build context, the path of the existing VM pipeline and an application-owned HTTP readiness endpoint.
- Resolve unknown assessment answers honestly. Stateful workloads require data/session/job redesign or a different adapter; setting a flag false is not remediation.
- Run application preparation. The agent exports the selected base commit to a temporary build context, rejects unsafe archive entries/symlinks, builds locally, starts with UID 10001/read-only root/dropped capabilities, and checks HTTP health twice. Failure yields a blocked report with **no application branch**. The application team can correct its source and retry.
- Success creates a separate application branch/worktree and leaves the source checkout and VM pipeline unchanged. Push only with explicit --push or ordinary reviewed Git commands.
- Import the application container pipeline. It repeats build/runtime validation, fails on HIGH/CRITICAL Trivy findings, pushes the built image and publishes a digest/source-revision/build-ID artifact. Scanning and Azure publication are separate CI gates, not claims made by the initial local runtime test.

## Artifact-driven AKS release

The infrastructure release pipeline subscribes to successful Package stages from the configured application pipeline and branch. It downloads the triggering run's artifact, checks schema, expected ACR repository, digest, source commit, run ID and passed containerization, then pins the digest as a stage output.

Staging deploys via Helm, waits for rollout, and runs an in-cluster HTTP smoke test. Production then waits for the named Ops/DevOps group and production Environment checks. It uses the same digest, not a new build or mutable tag.

Helm --atomic handles upgrade failures. If the subsequent Helm smoke test fails, the generated script rolls back to the previously deployed Helm revision; for a failed first installation it removes that release. This restores Kubernetes configuration, not external data. Review failed test-pod logs privately and keep the VM service available.

## Acceptance before real cutover

A two-response health check is not a business validation. Run critical user journeys, dependency permissions, session behavior, database correctness, scheduled job ownership, load/soak tests, failure/drain tests, telemetry and rollback drills in the target environment. Verify all rendered resource sizes, worker concurrency, startup times, readiness semantics and egress policies. Pin deployment/test image digests and tool versions for a controlled release.

No public Ingress or LoadBalancer Service is generated by default. Configure an approved TLS gateway, certificate handling and WAF/routing before exposing a workload. Read CUTOVER.md before switching traffic. The agent does not copy VM disks, transform arbitrary applications, transfer databases, change DNS or stop VMs.

## Troubleshooting

| Symptom | Next action |
|---|---|
| Blocked before branch | Read the report; resolve unknown risks, missing Dockerfile, Docker availability or runtime health failure. |
| Container builds but fails health | Inspect the private build log and reproduce with the same non-root/read-only restrictions; verify port, health path and dependencies. |
| Existing branch/worktree | Choose a new branch/worktree for a deliberate attempt; no forced overwrite is provided. |
| ACR push/pull denied | Check registry permission mode, separate build/kubelet identities and private DNS/network access. |
| Completion trigger missing | Check source pipeline/project/branch/stage name, source-run success, pipeline permissions and default branch of the infrastructure pipeline. |
| Artifact validation fails | Verify the selected triggering run and repository/digest/source/build metadata; do not bypass validation. |
| Pending production | A named Ops/DevOps engineer must approve; timeout rejects. Check Environment checks and group membership. |
| Pod admission/health fails | Check namespace restricted policy, UID/filesystem needs, quotas, resources, image architecture, network egress and dependencies. |
